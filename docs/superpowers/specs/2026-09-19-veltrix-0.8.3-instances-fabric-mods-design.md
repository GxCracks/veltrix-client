# VELTRIX 0.8.3 Instances, Fabric & Mod Manager – Design Specification

## Status
Conversational design approved by the user. This document is the written specification for the next VELTRIX 0.8.3 test update.

## Goal
Extend the existing VELTRIX launcher so it behaves like a real multi-instance Minecraft launcher while keeping the existing VELTRIX visual identity and Microsoft/Minecraft launch core.

The update must:
- remove the large account-status card from the Home screen;
- keep the user signed in across launcher restarts;
- allow selection of all normal Minecraft releases, excluding snapshots;
- make Fabric the default loader for new instances while still allowing Vanilla;
- provide fully isolated instances;
- provide one integrated mod browser for Modrinth and CurseForge;
- install compatible mods and confirmed dependencies into the selected instance;
- preserve the existing official Microsoft/Xbox/Minecraft authentication and launch flow.

## Product identity and release handling
- Product remains `VELTRIX Client`.
- Existing 0.8.3 redesign remains the visual base.
- The next downloadable test build should be distinguishable from the previous 0.8.3 test ZIP; use an internal/test identifier such as `0.8.3.1` until an official public release tag is chosen.
- No website redesign is part of this work.

## 1. Home screen changes
The Home screen must no longer show the large account/login card visible in the current test build.

Home should focus on:
- selected instance;
- selected Minecraft version;
- loader state (`Fabric` or `Vanilla`);
- PLAY button;
- concise runtime/compatibility status;
- optional cosmetics/store preview.

Account management belongs under the existing `Account` section.

No fake username may appear on Home. If the launcher has an authenticated Minecraft profile, small contextual identity text may be shown, but not as a large account panel.

## 2. Persistent Microsoft login
### Required behavior
After a successful Microsoft/Minecraft login, closing and reopening VELTRIX should restore the session automatically when possible.

VELTRIX must never store the Microsoft password.

Persist only the minimum refresh/session material required to renew the official OAuth session.

### Secure storage
Introduce a `SecureTokenStore` abstraction.

Windows behavior:
- secrets must be stored encrypted using a Windows-protected mechanism;
- preferred implementation is a DPAPI-backed store or equivalent Windows user-bound secret storage;
- plaintext refresh tokens must not be written to `launcher.properties`, logs, crash reports, or ordinary JSON files.

If secure storage is unavailable or corrupted:
- launcher still starts;
- existing cached secret is ignored;
- user is asked to sign in again;
- no crash occurs.

### Session restore
On startup:
1. load encrypted refresh material;
2. attempt normal OAuth refresh;
3. continue Xbox Live/XSTS/Minecraft Services/profile verification through the existing official flow;
4. if refresh is invalid/revoked, clear the unusable secret and show normal signed-out state.

`Logout` must clear both in-memory session state and persisted secure token material.

The existing Minecraft Services allowlisting / `Invalid app registration` condition must not be bypassed.

## 3. Minecraft version catalog
VELTRIX must load the official Minecraft version manifest and expose all entries whose type is `release`.

Exclude:
- snapshots;
- old_beta;
- old_alpha.

The version picker should:
- show newest releases first;
- allow search/filter;
- show whether Fabric metadata is available for the selected version;
- retain the selected version per instance.

Network failures must not erase already-known local instance metadata. The UI should show an offline/error state and continue displaying existing instances.

## 4. Instance system
### Instance model
Add a first-class `Instance` model with at least:
- stable ID;
- display name;
- Minecraft version;
- loader type (`FABRIC` or `VANILLA`);
- Fabric loader version when applicable;
- instance root directory;
- creation/update timestamps;
- optional custom Java/runtime settings;
- optional icon later, not required for first implementation.

### Storage layout
Each instance must be isolated under the VELTRIX data directory, e.g.:

```text
VELTRIX/
  instances/
    <instance-id>/
      instance.json
      game/
        mods/
        config/
        resourcepacks/
        shaderpacks/
        saves/
        screenshots/
        logs/
        options.txt
```

Each instance must use its own Minecraft game directory when launched.

### Instance management UI
Add an `Instances` surface that supports:
- create new instance;
- select instance;
- rename;
- launch;
- open instance folder;
- delete with confirmation.

The last selected instance should be restored after launcher restart.

Deleting an instance is destructive and must require explicit confirmation in the UI.

## 5. New instance creation
New-instance flow:
1. enter instance name;
2. choose Minecraft release;
3. loader defaults to `Fabric`;
4. user can switch to `Vanilla`;
5. when Fabric is selected, choose the recommended/latest compatible Fabric Loader automatically, with an advanced override only if practical;
6. create the isolated directory structure;
7. persist metadata;
8. make the new instance selectable immediately.

Fabric being the default must not remove the ability to create Vanilla instances.

## 6. Fabric integration
### Fabric metadata
Introduce a Fabric metadata service responsible for:
- checking loader versions for a Minecraft version;
- resolving a compatible loader;
- preparing the required Fabric launch profile/libraries using the existing launcher/version infrastructure.

Do not delegate launching to an external launcher such as Prism Launcher.

### Launching
For a Fabric instance:
- use the selected Minecraft version;
- install/resolve Fabric loader metadata and libraries as needed;
- launch using the instance-specific game directory;
- preserve the existing authenticated Minecraft session and launch coordinator where possible.

For Vanilla:
- use the normal version metadata and instance-specific game directory without Fabric loader arguments.

## 7. Unified Mods browser
The Mods page becomes a real mod manager tied to the currently selected instance.

### One search UI
Provide one search box and one result list containing both providers.

Each result must display a source badge:
- `Modrinth`
- `CurseForge`

Common result information where available:
- name;
- icon;
- short description;
- author/project owner;
- supported Minecraft version;
- supported loader;
- provider/source;
- install/update action.

### Compatibility filtering
Search/install must automatically respect the selected instance:
- Minecraft version must match the instance;
- for Fabric instances, result/file/version must support Fabric;
- Vanilla instances should not offer Fabric-only mods as directly installable.

A user may see an explanatory incompatible state rather than a broken install button.

## 8. Modrinth provider
Modrinth should work without user configuration.

Create a provider adapter, for example:
- `ModProvider` interface;
- `ModrinthProvider` implementation.

The provider is responsible for:
- search;
- compatible version/file lookup;
- dependency metadata;
- file download metadata.

Downloaded files must be written only to the selected instance's `game/mods` directory.

## 9. CurseForge provider
CurseForge uses the same `ModProvider` abstraction.

### API key setting
Add to Settings:
- `CurseForge API Key` field;
- connected/not-connected indicator;
- optional validation action.

The key must be stored via the same secure storage layer used for sensitive tokens, not as plaintext in ordinary launcher settings.

Without a key:
- Modrinth still works normally;
- CurseForge provider is marked `Not connected`;
- unified search still functions using available providers;
- no repeated error popups.

With a valid key:
- CurseForge results participate in the same search result list.

## 10. Dependency confirmation
Before installing a selected mod, resolve required dependencies for the exact compatible file/version.

If dependencies are required, show one confirmation dialog listing them, for example:

```text
Install Sodium?

Required dependencies:
- Fabric API
- Cloth Config

[Cancel] [Install all]
```

Only after confirmation may VELTRIX download the main mod and required dependencies.

Rules:
- required dependencies are selected automatically for the confirmation list;
- optional dependencies are not silently installed;
- unresolved required dependencies stop installation with a clear explanation;
- duplicate already-installed compatible dependencies should not be downloaded again unnecessarily.

## 11. Mod installation safety
Before writing a mod file:
- resolve the final compatible version/file;
- sanitize file names;
- write to a temporary file first;
- verify the download completed;
- move atomically into `mods` where practical.

A failed download must not leave a zero-byte or partial `.jar` presented as installed.

The Mods page should indicate installed state based on the selected instance.

## 12. Mod updates and removal
First implementation should support:
- detect a mod installed by VELTRIX through local metadata;
- remove a mod from the selected instance;
- replace/update it when a newer compatible provider version is deliberately selected.

VELTRIX should maintain lightweight per-instance mod metadata so it can distinguish managed downloads from unrelated manually-added JARs.

Manually-added mod JARs must not be deleted or overwritten without explicit user action.

## 13. Settings additions
Settings gains:
- CurseForge API Key control;
- default loader display (`Fabric`);
- instances root path display/open-folder action;
- optional download concurrency limit only if needed by implementation.

Do not overload Settings with advanced controls that are not required for this release.

## 14. Navigation and visual design
Keep the approved VELTRIX 0.8.3 design:
- black/anthracite base;
- cyan on left/primary emphasis;
- purple on right/secondary emphasis;
- supplied V logo;
- same custom title bar/window shell.

Navigation should expose instance management clearly. It may use the existing `Versions` area for catalog selection and add/rename a dedicated `Instances` entry if that gives a clearer UX.

The implementation may adjust navigation labels/layout without changing the visual identity.

## 15. Error handling
All networked services must fail gracefully.

Examples:
- Mojang version manifest unavailable → show cached/local information;
- Fabric metadata unavailable → prevent Fabric creation for that version with explanation;
- Modrinth unavailable → CurseForge can still work if configured;
- CurseForge key absent/invalid → provider disabled, launcher remains usable;
- mod download failure → show error, leave instance usable;
- secure token storage failure → signed-out state, no launcher crash.

Do not block launcher startup solely because a mod provider is offline.

## 16. Architecture
Recommended components:

```text
InstanceManager
InstanceRepository
MinecraftVersionCatalog
FabricMetadataService
SecureTokenStore
WindowsSecureTokenStore
ModSearchService
ModProvider
  ├─ ModrinthProvider
  └─ CurseForgeProvider
ModInstallService
DependencyResolver
ManagedModRepository
```

`ModSearchService` merges provider responses into a common UI model.

`ModInstallService` performs compatibility checks, dependency resolution, confirmation input, downloads, and local managed-mod metadata updates.

Authentication services should depend on `SecureTokenStore` instead of the current memory-only token persistence implementation.

## 17. Existing systems to preserve
Do not intentionally rewrite or bypass:
- Microsoft OAuth PKCE behavior;
- Xbox Live authentication;
- XSTS authentication;
- Minecraft Services authentication;
- ownership/profile checks;
- current launch diagnostics/crash logging;
- Java runtime detection;
- the approved 0.8.3 visual redesign;
- installer startup smoke tests.

Where launch changes are required for instance-specific game directories or Fabric, adapt the existing coordinator rather than replacing unrelated authentication logic.

## 18. Data migration
Existing users with no instances should get a clean first-run state.

If an existing launcher configuration already contains a selected Minecraft version, VELTRIX may offer/create a default instance from it, but migration must not move or delete the user's existing `.minecraft` content automatically.

No existing worlds or mods may be silently relocated.

## 19. Testing requirements
Before distributing the next test build, verify at minimum:

1. Home account card is absent.
2. Existing Account screen remains usable.
3. secure token store never writes raw refresh token into ordinary config/log files.
4. successful stored session can be restored through the normal refresh path.
5. logout clears persisted session secret.
6. version catalog contains releases and excludes snapshots.
7. new instance defaults to Fabric.
8. Vanilla instance can still be created.
9. two instances have separate `mods`, `config`, `saves`, and options state.
10. last selected instance persists across restart.
11. Fabric metadata resolution works for a supported release and fails cleanly for unsupported/unavailable metadata.
12. Modrinth search filters by selected Minecraft version and Fabric.
13. CurseForge without API key does not break unified search.
14. CurseForge API key is stored through secure storage.
15. unified results identify provider source.
16. required dependencies are shown before installation.
17. cancelling dependency confirmation downloads nothing.
18. confirming installs main mod plus required dependencies into only the selected instance.
19. partial download does not remain as an installed mod.
20. manually-added unknown mod files are not deleted automatically.
21. existing malformed-settings/startup regression still passes.
22. launcher opens successfully at the existing minimum window size.
23. final test ZIP/installer starts on Windows and preserves the redesigned UI.

## 20. Non-goals for this iteration
- importing complete CurseForge/Modrinth modpacks;
- automatic server mod synchronization;
- NeoForge/Forge/Quilt support;
- cloud instance synchronization;
- account/password storage;
- bypassing Minecraft Services application approval;
- changing the website.

These can be separate later features.

## Success criteria
This update is successful when a user can reopen VELTRIX and remain signed in, create isolated Fabric or Vanilla instances using any normal Minecraft release, select an instance, search Modrinth and optionally CurseForge from one Mods page, review required dependencies, install them into that instance, and launch through the existing official Minecraft authentication path without affecting other instances or the user's unrelated `.minecraft` files.
